### S1: Steam virtual pad order ↔ physical controllers (**blocking**)
- **Q:** With Steam Input on, can we work out which Steam Virtual Gamepad index corresponds to which physical controller? Does the emulator's SDL index order match Steam's player order?
- **Method:** Connect Deck + DS4 + 8BitDo in various orders. Dump `/proc/bus/input/devices`, `/sys/class/input/*/device/{name,uniq,phys,id/*}` for virtual and physical devices. Check whether virtual devices expose any link (uniq/phys/serial) to the physical one. Run `sdl2-jstest --list` (or a tiny SDL script) inside the Flatpak sandbox (`flatpak run --command=...`) to see the emulator's view. Use Steam's "Reorder controllers" and re-check.
- **Findings (desk research, mechanism confirmed in source):** SDL 2.30+/SDL3 read the file Steam names in the `SteamVirtualGamepadInfo` env var (`~/.local/share/Steam/config/virtualgamepadinfo.txt`). It has one `[slot N]` section per virtual pad with `name`, `VID`, `PID`, `type` and `handle`. Virtual pads are uinput `28de:11ff` devices named `Microsoft X-Box 360 pad N`, and SDL maps N → slot → the physical pad's name/VID/PID/type. The GUID stays the virtual one. `mh-run` inherits these env vars, so it can do the same mapping (see [04 §5.2](04-controller-identification.md)). Steam recreates virtual pads at every launch, so the probe must run after they exist. **Still needs a device:** whether slot N equals player order after "Reorder controllers"; whether SDL index order matches slot order inside each emulator; telling two identical pads apart; whether the env var and file reach Flatpak sandboxes. Sources: [SDL_steam_virtual_gamepad.c](https://github.com/libsdl-org/SDL/blob/8adc0f98837db84fd24f17c339e59dcf36a17156/src/joystick/SDL_steam_virtual_gamepad.c), [SDL#14410](https://github.com/libsdl-org/SDL/issues/14410)
- **On device (2026-10-22, `dualsense-bt`):** a slot's `handle` holds the physical pad's Bluetooth MAC in its low 48 bits (checked against `uniq`): `0x000d<MAC>` for the DualSense, `0x0000<MAC>` for the Switch Pro (`switchpro-usb`); the Deck's own slot is `0x000000ff35010bbe`). That links each Steam slot to one exact physical pad, even two of the same model; `SteamSlot.device_id` and `map-helper devices` (`steam_slot=`) use it. Over USB (`dualsense-usb`) the handle is identical, so the link doesn't depend on the transport. Still to check: whether slot order follows Steam's "Reorder controllers".
- **On device (2026-10-22, `8bitdo-u2-usb`):** a wired X-input pad's handle is `0x1<VID><PID>` plus 7 hex digits, with no MAC (and its gamepad node has no `uniq`), so it's linked by VID:PID when that's unique. Steam **keeps a slot for a pad that disconnected**: slot 1 (the 8BitDo over BT, then switched off) stayed in the file with no `pad 1` virtual node, and the wired pad took slot 2. A slot without a virtual node is stale.
- **On device (2026-10-22, `all-three`):** DualSense (BT), 8BitDo (BT) and Switch Pro (USB), turned on in that order, got slots 1, 2, 3 in that order, each linked to its physical pad by handle. The stale slots seen in `8bitdo-u2-usb` were gone, so Steam drops them at some point (when exactly is unknown).
- **On device (2026-10-22, `all-three-reordered`):** Steam's "Reorder controllers" rewrites the slot file at once: Switch Pro, 8BitDo, DualSense, Deck became slots 0–3, and the virtual pads are re-fed to match (virtual pad 0, `event10`, was the Deck and is now the Switch Pro). So the slot file is the truth for "which physical pad is player N" at launch, the Deck itself can be any player, and slot order is not connection order once the user has reordered. Handles, and so the linked ids, don't change. **Answered.**
- **On device (2026-10-22, Game Mode, RetroArch Flatpak with the `sdl2` driver, Snes9x):** after an in-game "Reorder controllers" put the DualSense in Steam slot 0, RetroArch's user 1 was still **the Deck**. RetroArch had all three virtual pads open; user 1 was `Microsoft X-Box 360 pad 1` (`event18`/`js0`, the Deck), not `pad 0` (`event25`/`js5`, the DualSense), so its order follows device enumeration (lowest node first), not Steam's slots or the `pad N` names. A remap written for "player 1 = DualSense" applied to the Deck (verified in Mega Man X: the swap worked on the Deck's buttons). **Consequence:** map from physical pad to an emulator's player number via the emulator's own enumeration (Steam slot -> virtual node through the handle, then node order), never Steam slot N = player N+1. **[VERIFY]** whether this holds after a fresh boot with no reorder, and for Dolphin's `SDL/<n>` indices.
- **Findings (desk research, 2026-10-22, SDL's two orders):** SDL ≥ 2.30 and SDL3 enumerate Steam virtual pads first, sorted by the `<N>` in `pad <N>` (`LINUX_ScanSteamVirtualGamepads`, SDL commit 5b26d4e, first in 2.30.0), then the rest by js index; older SDL2 sorts everything by js index (`sort_entries`). With the info file, the newer SDLs also rename the pad after its slot. Dolphin bundles SDL3, so its order should follow the slots. map-helper models both orders per adapter ([04 §5.2](04-controller-identification.md), "From Steam slot to emulator index"). (This entry first guessed that RetroArch's Flatpak ships SDL < 2.30; the on-device check below shows it doesn't.) Sources: [SDL2 release-2.30.x SDL_sysjoystick.c](https://github.com/libsdl-org/SDL/blob/0aef2c3612294b8ed4fb9626b8426f4c9c835c6d/src/joystick/linux/SDL_sysjoystick.c#L854-L1000), [SDL3 at Dolphin's Externals/SDL](https://github.com/libsdl-org/SDL/blob/fa2c02bb6e21974a89ea9824bc53c9932abe5f9c/src/joystick/linux/SDL_sysjoystick.c#L867-L965), [RetroArch sdl2_joypad.c](https://github.com/libretro/RetroArch/blob/eb7335f939c39be703662c2a0e07c106f99b64ac/input/drivers_joypad/sdl2_joypad.c#L334-L339)
- **On device (2026-10-22, RetroArch's SDL):** the RetroArch Flatpak (1.22.2, runtime `org.kde.Platform` 6.11) loads the runtime's `/usr/lib/x86_64-linux-gnu/libSDL2-2.0.so.0.3200.68` (464 KB, next to `libSDL3.so.0.2.30`): sdl2-compat over SDL3 3.2.30, not SDL < 2.30. The Flatpak has `host` filesystem access and can read `virtualgamepadinfo.txt`. So the node order seen above happened despite SDL3 underneath; why SDL3's slot sort didn't apply is unknown **[VERIFY]** (maybe `SteamVirtualGamepadInfo` isn't in the Flatpak's environment, or the sdl2-compat path differs). map-helper keeps `nodes` for RetroArch because that observation is the evidence.
- **On device (2026-10-22, Game Mode, docked, fresh session, no reorder):** Steam slots were 0 DualSense, 1 Deck, 2 Switch Pro, and the virtual pads were in the same order by node (pad 0 lowest, then pad 1, then pad 2). RetroArch's user 1 was the DualSense (owner confirmed in game). That agrees with both orders, so it doesn't tell `nodes` from `slots`. `map-helper devices` read `policy: external-first (docked: DP-1 connected)` and gave player 1 = DualSense (RetroArch port 0, `SDL/0/DualSense Wireless Controller`), player 2 = Switch Pro (port 2), player 3 = Deck (port 1).
- **On device (same run, Dolphin, EmuDeck AutoMap on):** at launch AutoMap wrote, in Steam slot order, GCPad1 `SDL/0/DualSense Wireless Controller`, GCPad2 `SDL/0/Steam Deck Controller`, GCPad3 `SDL/0/Nintendo Switch Pro Controller`, GCPad4 the Deck again (with `SIDevice3 = 0`), and `[Hotkeys] Device` = the DualSense. The owner confirmed in game that the DualSense is player 1. So Dolphin (SDL3) names each pad after its Steam slot and uses `n = 0` per distinct name, exactly as map-helper's `slots` model computes. **Answered** for names and index; the order when the nodes are out of slot order is still **[VERIFY]**. AutoMap also reset the face buttons and Z to EmuDeck stock (the owner's Z = `Shoulder R`|Back was lost), which is what `doctor` warns about.
- **On device (2026-10-22/23, Game Mode, handheld, write test with `apply --write` then `restore`):** Deck, 8BitDo (BT) and DualSense (BT). The planned Switch Pro in slot 0 wasn't possible: outside a game, Game Mode offers no "Reorder controllers" (the owner found it only in-game), so the order was whatever Steam gave. Four launches:
  1. **RetroArch, Mega Man X (Snes9x), launching pad not noted.** Written for slots Deck 0, 8BitDo 1, DualSense 2 (`input_player1..3_joypad_index` = 0, 1, 2). In game only the **DualSense** moved player 1. Steam had rewritten `virtualgamepadinfo.txt` 18 s after RetroArch started, to DualSense 0, 8BitDo 1, Deck 2, and `devices` then showed virtual pad 0 (`event10`) fed by the DualSense. RetroArch's *Settings → Input → RetroPad Binds → Port N* showed Device Index "Steam Virtual Gamepad (1)/(2)/(3)" (the suffix only numbers duplicate names). So index 0 followed the new slot 0, and the config written before the rewrite was stale.
  2. **`SteamVirtualGamepadInfo` reaches RetroArch's Flatpak environment:** present, pointing at `~/.local/share/Steam/config/virtualgamepadinfo.txt` (the same file `map-helper` reads outside a game); `SDL_GAMECONTROLLER_IGNORE_DEVICES` present too. This rules out the "env var missing" explanation above.
  3. **RetroArch again, launched with the 8BitDo only.** On exit from launch 1, Steam had put the order back (Deck 0, 8BitDo 1, DualSense 2), and the config matched it. A watcher polling the slot file every 0.5 s saw **no rewrite** from before the launch until well after RetroArch started, yet only the **8BitDo** moved player 1 (expected: the Deck). RetroArch had exactly the three virtual nodes open, in node order. Whether Steam re-fed virtual pad 0 from the launching pad without rewriting the file, or SDL ordered them some other way, is unknown **[VERIFY]**; a per-node button recorder was started but lost when its ssh session was killed.
  4. **Dolphin, a GC game, launched with the 8BitDo.** Steam rewrote the slot file 9 s **before** Dolphin started, putting the 8BitDo in slot 0. Dolphin's GCPad1 was pinned by name to `SDL/0/Steam Deck Controller`, and the Deck (not the 8BitDo) was player 1, as written. **Dolphin's name pinning holds across a Steam reorder.**
- **On device (2026-10-23, Steam's own logs for the sessions above, read-only):** Steam logs its slot changes in `~/.local/share/Steam/logs/console_log.txt`: `Created/Destroyed virtual controller at slot S for controller C` when a pad connects or goes away, `Seating controller C in slot S` while a game runs, and `Controller slots reset` when the game exits (`gameprocess_log.txt` `Game process removed` in the same second). `C` is Steam's own controller number (the Deck was 0, then 1 and 2 for the pads in the order they connected), not a slot. **Every launch of the write test ran inside ES-DE** (Steam app 3996473244; RetroArch and Dolphin are its children), and in each ES-DE session Steam seated the pads one at a time, slot 0 first, seconds to minutes apart: 19:06:45 ES-DE starts, 19:07:30 DualSense to slot 0, 19:10:57 8BitDo to slot 1, 19:11:18 Deck to slot 2 (launch 1: the rewrite seen 18 s after RetroArch started is this first seating); 09:05:20 ES-DE starts, 09:05:34 8BitDo to slot 0 (launch 3). The one Steam game launched that day (app 1817230) was seated 68 s after it started. So Steam seats a pad **at its first input in the game session**, in input order, rather than moving "the launching pad" at launch; a pad that's never used is never seated. Reading: the launching pad becomes player 1 when it's the first pad used after the session starts, and for a launch from ES-DE the session is ES-DE's, so the order is settled (or not) by whatever was pressed in ES-DE before the game. mh-run's `launch.log` now records the player order it used and the slot file's age; `tools/deck.sh watch` records presses per node, slot rewrites and process starts.
- **On device (2026-10-23, mh-run installed, ES-DE hook, Game Mode, handheld; Deck, DualSense and 8BitDo over BT):** **ES-DE navigation seats a pad.** 09:59:13 ES-DE starts; 09:59:25 the 8BitDo (used to navigate ES-DE, nothing else touched) is seated in slot 0; 09:59:42 mh-run's ES-DE hook for RetroArch (Mega Man X, Snes9x) logs `order=8bitdo.ultimate2,sony.dualsense,valve.steamdeck slots_age=16.8 ms=134`, and the 8BitDo was player 1. Presses in game seated the DualSense (09:59:53, slot 1) and the Deck (10:00:13, slot 2). Then a GameCube game **launched with the DualSense** from the same ES-DE session: mh-run (10:00:39, `ms=133`) wrote GCPad1 `SDL/0/8Bitdo Ultimate 2 Wireless Controller` (it was the Deck before), GCPad2 the DualSense, GCPad3 the Deck, and the **8BitDo was player 1**, not the launching DualSense. Dolphin kept those lines when it saved its config on exit. So within one ES-DE session the order is fixed by first use, whichever pad launches each game.
  - **Rule (the owner's decision, 2026-10-23, replacing "the launching pad" of 2026-10-22):** player 1 is **Steam's order**, i.e. the first pad used since the Steam game (ES-DE, or a Steam shortcut) started. It matches Steam's own player numbering and player lights, and what RetroArch does on its own; to change player 1, restart ES-DE with that pad. mh-run already does this (it probes at launch and follows the slots). The alternative, a helper that runs while ES-DE is open and remembers the last pad pressed, was turned down (a resident process, against ADR-001). For a Steam shortcut, nothing is seated when mh-run runs (app 1817230 was seated 68 s in), so mh-run sees the order left from before; **[VERIFY]** with a Steam shortcut that runs mh-run.
  - **RetroArch rewrites a managed `.rmp`:** with `remap_save_on_exit = "true"` (EmuDeck's setting here), quitting RetroArch saved its in-memory remap over `Snes9x.rmp`, dropping player 2's swap and adding ~20 unmanaged keys (`input_libretro_device_pN`, `input_remap_port_pN`, turbo settings). The writer's "someone else replaced a file we created" rule then treated RetroArch's save as the user's file: the manifest flipped to `created: false`, RetroArch's version became the pristine one, and `restore` left the file in place (removed by hand). Not a security issue, but `restore` was wrong. Fixed: the writer and restore now tell RetroArch's own save apart ([adapters/retroarch.md](adapters/retroarch.md), "Load precedence and save behaviour").
  - Restore check: every Dolphin ini and `retroarch.cfg` were byte-identical to a copy taken before the test, except Dolphin's own `Qt.ini` and `TimePlayed.ini`, which Dolphin writes when it runs.

### S2: Detecting passthrough vs native mode (**blocking**)
- **Q:** At launch time, how do we reliably know whether a given physical controller is behind Steam Input?
- **Method:** Toggle Steam Settings → Controller → PlayStation support, and per-game "Disable Steam Input" on an SRM shortcut. Observe device lists and Steam config files (`~/.steam/steam/config/config.vdf`, `~/.steam/steam/userdata/<id>/config/localconfig.vdf`).
- **Findings (desk research):** Steam puts the VID/PIDs of the physical pads it virtualises in `SDL_GAMECONTROLLER_IGNORE_DEVICES` in the game's environment. A pad on that list is behind Steam Input (passthrough); a pad not on it is native. Use the ignore list first, then the virtual gamepad info file. `localconfig.vdf` (`SteamController_PSSupport` / `_XBoxSupport` / `_SwitchSupport` / `_GenericGamepadSupport`, per-app `UseSteamControllerConfig` 0/1/2, which also applies to non-Steam shortcuts) is advisory only. Sources: [Proton#4707](https://github.com/ValveSoftware/Proton/issues/4707), [steammessages_clientsettings.proto](https://github.com/SteamTracking/Protobufs/blob/5c2b73b24be75d4e0f85889cea48bd669916767f/steam/steammessages_clientsettings.proto), [SRM controller-manager.ts](https://github.com/SteamGridDB/steam-rom-manager/blob/f68289a770ff8537ac8235618b3399844580359b/src/lib/controller-manager.ts)
- **On device (2026-10-22, `dualsense-bt`):** `virtualgamepadinfo.txt` exists at `~/.local/share/Steam/config/` outside any game, with `[slot 0]` = the Deck (`28de:1205`, `type=steam`) mapped to `Microsoft X-Box 360 pad 0` (`28de:11ff`, `event10 js0`). Its `name` is a localization token, `#SettingsController_SteamController`, not a display name, so the UI must label Valve pads itself.
- **On device (2026-10-22, `game-steam-input-on` / `game-steam-input-off`):** this contradicts the desk finding. In a running game's environment (Dolphin launched by ES-DE from a Steam shortcut) `SDL_GAMECONTROLLER_IGNORE_DEVICES` has **793 entries: every pad type Steam supports**, connected or not, so being on it doesn't mean a pad is connected or virtualised. With "Disable Steam Input" set for that shortcut the environment is **byte-identical**: same list, same variables. SDL still ignores the physical pads while Steam stops feeding the virtual ones, so the game gets no input at all (EmuDeck's Dolphin binds `SDL/0/Steam Deck Controller`). The per-game override wasn't in `localconfig.vdf` 14 minutes after setting it (Steam may flush later, or keep it elsewhere; **[VERIFY]**). Consequences: `map-helper devices` now treats a pad with a live Steam slot as behind Steam, using the ignore list only without a slot file; `mh-run` can't detect the override from the environment, and a per-game "Disable Steam Input" on an EmuDeck shortcut breaks all input. `doctor` now reports it from `localconfig.vdf` `apps/<unsigned id>/UseSteamControllerConfig` (the key SRM writes); whether Steam writes the Game Mode override there, and when, is still **[VERIFY]** (capture steps in [05](05-steam-input-strategy.md#the-per-game-override-in-doctor)).

### S3: Can we read physical input for capture in Game Mode? (**blocking for Phase 3**)
- **Q:** Does Steam grab evdev for each controller type? Can the Decky backend (as root or the deck user) read `/dev/input/event*` or `/dev/hidraw*` while Steam is running?
- **Method:** `evtest` / a small python-evdev-free reader (raw struct read) on each controller's node while in Game Mode; check `EVIOCGRAB` behaviour.
- **Findings (desk research, partial):** Steam reads Sony, Nintendo and Valve pads through hidraw, and Valve's udev rules grant exactly those devices. hid-steam removes the Deck's evdev gamepad while Steam runs. Steam needing the ignore list to filter physical pads suggests it doesn't grab evdev, but that's inference. The `deck` user can read gamepad evdev nodes (uaccess, see S12/[14](14-packaging-permissions.md)). **Still needs a device:** the Xbox evdev grab. Sources: [60-steam-input.rules](https://github.com/ValveSoftware/steam-devices/blob/22ec85e5ff5ea2e15c56d71a41bcbef46356cd60/60-steam-input.rules), [hid-steam.c](https://github.com/torvalds/linux/blob/2a08195e4db5aba84600db6518089a1dbe2d04c7/drivers/hid/hid-steam.c)
- **On device (2026-10-22, SteamOS 3.8.28, `tests/fixtures/devices/dualsense-bt`):** confirmed that with Steam running the Deck's own controls expose no evdev gamepad, only `28de:1205` mouse and keyboard nodes. The DualSense's motion-sensor node has a `js` handler too; it's told apart by `INPUT_PROP_ACCELEROMETER` (`B: PROP=40`). Xbox evdev grab still untested (no Xbox pad on hand).

### S4: Decky UI input trapping
- **Q:** In a Decky full-screen route, can we consume all gamepad buttons (including B/back and the shoulders) without Steam navigating?
- **Method:** Prototype a route with `Focusable` + `onGamepadButtonDown` / `onButtonDown`, log events, and check whether back closes the route.
- **Findings (desk research):** `@decky/ui` 4.16 `FooterLegend.ts` exposes `onButtonDown`, `onCancelButton` and the `GamepadButton` enum (including L4/L5/R4/R5). `onGamepadButtonDown` doesn't exist. SteamGridDB's full-screen `LogoPositionerModal.tsx` takes over B, X, Y, Menu and the D-pad by handling them on a `Focusable`, so B and the shoulders look capturable; the Steam and QAM buttons likely aren't. **UI events carry no controller index**, so the actual bind must come from evdev in the backend. Toasts have a single `onClick`, so Flow 1 opens a modal. Source: https://github.com/SteamDeckHomebrew/decky-frontend-lib/blob/10b929d2e92af179569fa1bb8f456cc5f57f28d5/src/components/FooterLegend.ts. **Still needs a device:** whether B/back is fully consumed.

### S5: EmuDeck launchers and launch paths (**blocking**)
- **Q:** Current location, structure and args of `~/Emulation/tools/launchers/*.sh`; what SRM shortcuts and ES-DE find rules execute; whether EmuDeck updates overwrite launchers.
- **Method:** Inspect files, run an EmuDeck update, diff. Check whether non-Steam shortcut launch options support `%command%`.
- **Findings (desk research, EmuDeck `dragoonDorise/EmuDeck@dddb302`):** Launchers live in `$toolsPath/launchers/<emu>.sh` (default `~/Emulation/tools/launchers/`) and are copied to `$romsPath/emulators/`. Each runs `git pull` on the backend, sources `all.sh`, calls `launcherInit` and `emulatorInit <emu>`, then runs the emulator with `"$@"` (see `tests/fixtures/emudeck-launchers/`). `launcherInit` → `update_launchers` restores every launcher at each launch, and `emulatorInit` runs `git reset --hard`, so **patching launchers can't work**. There's no pre-launch hook. SRM shortcuts all point at launchers (except Vita3K). ES-DE's find rules route only Dolphin, Cemu, ShadPS4, Ryujinx and Xenia through launchers; RetroArch, PCSX2 and DuckStation launch directly. Non-Steam shortcuts support `%command%` (EmuDeck's Dolphin/Cemu/Switch parsers use `vblank_mode=0 %command% …`). AutoMap rewrites Dolphin input at launch. Decision revised in [ADR-001](adr/001-apply-at-launch.md). Sources: `tools/launchers/`, `functions/helperFunctions.sh` (`update_launchers`, `emulatorInit`), `configs/steam-rom-manager/userData/`, `configs/emulationstation/custom_systems/es_find_rules.xml`; ES-DE `resources/systems/linux/es_find_rules.xml` and INSTALL.md "Custom event scripts". **Still needs a device:** AutoMap behaviour with GUI defaults, ES-DE `game-start` timing, `%command%` expansion when Exe has args.

### S7: EmuDeck's default bindings and hotkeys
- **Q:** What exactly do EmuDeck's shipped configs bind (per emulator)? We need these to author `data/defaults/` that reproduce them.
- **Method:** Read `~/.config/EmuDeck/backend/configs/**` (**[VERIFY]** location), diff against fixtures.

### S8: Controller identity details
- **Q:** VID:PID and names for each controller and mode (8BitDo X/S/D/A modes, wireless dongles), `uniq` contents over USB vs BT, whether a DS4/DualSense's USB connection exposes its BT MAC.
- **Method:** Dump sysfs for each scenario; read HID feature reports via hidraw.
- **Findings (desk research):** VID:PID tables are in `data/controllers.json` with sources. hid-playstation and hid-nintendo set `uniq` to the Bluetooth MAC over **both USB and BT** (DS4 feature report 0x12, DualSense/Edge 0x09), so Sony/Nintendo pads need no manual USB↔BT linking. xpad never sets `uniq` and names devices from its own table, so an 8BitDo in X-mode on `045e:028e` won't show "8BitDo" in its name. The 8BitDo SN30 Pro+ over BT presents as Xbox One S `045e:02e0`. **Still needs a device:** 8BitDo macOS mode, dongles in X/Switch mode, MAC OUIs, M30/Ultimate PIDs, `uniq` of Sony adapter `0ba0`. Source: [hid-playstation.c](https://github.com/torvalds/linux/blob/2a08195e4db5aba84600db6518089a1dbe2d04c7/drivers/hid/hid-playstation.c)

The device name differs (`DualSense Wireless Controller` over BT, `Sony Interactive Entertainment DualSense Wireless Controller` over USB), so name matching must not be exact. Over USB `phys` is empty. Stable ids are now `mac:<addr>` on both transports (docs/04 §1.2; the code had used `bt:`/`usb-serial:`).
- **On device (2026-10-22, `switchpro-usb`):** hid-nintendo's `uniq` is the Bluetooth MAC over USB too, on the gamepad and `(IMU)` nodes. The IMU node has no `js` handler here. `057e:2009` is flagged ambiguous, so the Pro shows `[needs claim]` until the 8BitDo test says whether that's needed.
- **On device (2026-10-22, `8bitdo-u2-bt`):** the 8BitDo Ultimate 2 Wireless in Bluetooth mode is `2dc8:6012` named `8BitDo Ultimate 2 Wireless`, with its Bluetooth MAC in `uniq` (the Steam slot handle links to it like the Sony and Nintendo pads). Steam reports `type=unknown`. It does not impersonate a Switch Pro in this mode, and the model has no Switch mode, so the `057e:2009` ambiguity stays **[VERIFY]**.
- **On device (2026-10-22, `8bitdo-u2-usb`):** the Ultimate 2 Wireless wired is `2dc8:310b` (`8BitDo Ultimate 2 Wireless Controller`, plus `... for PC Keyboard` and `Mouse` nodes); the gamepad node (xpad) has an **empty** `uniq`; only the keyboard and mouse HID nodes carry the 10-hex-digit USB serial (equal to sysfs `serial`). Reading the USB device's sysfs `serial` (docs/04 §1.2 step 2) makes it `usb-serial:2dc8:310b:<…>`, stable across ports (done, tested on constructed sysfs trees; the capture now records sysfs `serial` in `usb-devices.tsv`, so re-capture `8bitdo-u2-usb` handheld and docked to confirm); linking it to the BT id stays a manual "link identities" case.

Pads that only have a `path:` id, like the wired 8BitDo, would change id when docked; reading the USB `serial` fixes that.

- **Q:** Most reliable signal: `/sys/class/drm/card*-DP-*/status`, external power, USB hub presence?

### S11: Emulator-running detection under Flatpak/AppImage
- **Q:** How to reliably detect that an emulator is running (process names for `bwrap` children, AppImage mount paths)?
- **Findings (desk research):** Flatpak runs each app in a systemd scope `app-flatpak-<id>-<instance>.scope` (`flatpak-run.c`) and keeps `$XDG_RUNTIME_DIR/.flatpak/<instance>/{info,bwrapinfo.json}` (`flatpak-instance.c`). ### S12: Python environment
- **Q:** SteamOS Python version; Decky backend Python version and sandboxing; can the Decky backend run `mh-core` as a library?
- **Findings (desk research):** Decky is a single PyInstaller binary. v3.3.0 bundles Python 3.14.8 (v3.2.x: 3.11.7) with only part of the stdlib (issue #968: v3.2.9 dropped `http.server`, `glob`, `configparser`). ### S13: Game id sources
- **Q:** For PCSX2/DuckStation (CHD, ISO), Dolphin (RVZ, ISO), RetroArch: what does each emulator's game list cache contain and in what format? Is `dolphin-tool` available in the Flatpak?
- **Findings (desk research):** **Dolphin:** 6-char ID at bytes 0–5 of ISO/GCM, and at offset 0x58 of WIA/RVZ (magic `WIA\x01`/`RVZ\x01`). GCZ needs `dolphin-tool header -j -i <file>` (JSON with `game_id`). Dolphin's `gamelist.cache` is an unstable binary dump, so don't parse it (`WIABlob.h` L81–119, `HeaderCommand.cpp`). **PCSX2:** `cache/gamelist.cache`, signature `0x45434C47`, version 34; entries hold path, serial, titles, type, region, size, mtime, u32 crc (`GameList.cpp` L509–640). **DuckStation:** `cache/gamelist.cache`, signature `0x45434C48`, version 41; entries hold type, region, path, serial, title, hash, sizes, mtime, disc-set index (`game_list.cpp` L746–801). Both caches are little-endian, with strings stored as a u32 length then bytes. **Still open:** first-disc serial for DuckStation multi-disc sets.
